## 一句话总结

用随机程序生成器（Varity 扩展版）生成数十万个微型 Kernel，在 NVIDIA (V100) 与 AMD (MI250X) 两大超算平台上做**跨平台差分测试**，揭示了由**数学库底层实现（libm/OCML）、编译器指令重排、浮点精度路径和代码转译工具（HIPIFY）**引起的隐蔽数值分歧。

### 关键实现细节（论文的精妙之处）
1. **测试用例形态**：每个生成的程序极其短小（单 Kernel 函数 `compute`），包含基本算术 `{+, -, *, /}`、C 数学库函数、`for` 循环嵌套和 `if` 分支，最终将标量结果通过 `printf("%.17g\n", comp)` 输出为 17 位有效数字的字符串比对。
2. **跨机房解耦测试（Figure 3）**：两套 GPU 通常不在同一集群。作者用 **JSON 元数据机制**：在 Cluster 1 生成并运行完后，将输入、编译选项和运行结果打包存入 JSON；复制到 Cluster 2 后读取该 JSON，用相同的参数和输入再跑一遍并追加记录。
3. **Fast-Math 的“隐形非对等”**：
   * CUDA 使用 `-ffast-math` 运行顺畅；
   * 但 AMD ROCm 的 `hipcc` 开启 `-ffast-math` 时，其内含的 `-ffinite-math-only` 会导致处理 NaN/Inf 时直接出错或崩溃。因此 ROCm 官方建议在 HIP 侧改用 **`-DHIP_FAST_MATH`** 宏。
   * **启示**：跨平台对比时，“同名”编译优化开关往往并不等价！

## 核心实验结果与发现

### 整体统计表（Table IV）

| 配置 | 测试程序数 | 总运行次数 | 发现差异次数 | **差异率** | 核心特征 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **FP64 (双精度)** | 3,540 | 247,500 | 2,426 | **0.98%** | 绝大多数为 `Num↔Num` 真实漂移 |
| **FP64 + HIPIFY 转译** | 3,540 | 247,500 | 2,716 | **1.10%** | **转译工具自身引入了额外的数值分歧** |
| **FP32 (单精度)** | 2,840 | 157,600 | 14,188 | **9.00%** | **差异率激增近 10 倍！** |

### 核心观察结论
1. **无优化（`-O0`）绝不代表数值一致**：FP64 下 `-O0` 出现了 440 次差异；FP32 下 `-O0` 也有 45 次差异。说明**平台底层的数学函数库实现和微架构本就不同**，不完全是编译优化的锅。
2. **FP32 + Fast-Math 是“数值灾难区”**：在 FP32 差异的 14,188 次中，有 **13,877 次**（占 97.8%）集中爆发在 `-O3 -ffast-math` 下，且伴随大量 `NaN↔Inf`、`Num↔Zero` 的剧烈坍塌。
3. **7 类结果分类矩阵（Table V & Table IX）**：
   * 分类：`NaN↔Inf`、`NaN↔Zero`、`NaN↔Num`、`Inf↔Zero`、`Inf↔Num`、`Zero↔Num`、`Num↔Num`。
   * 把 **Zero 单独剥离**是极具洞察力的设计：能够精准捕获**下溢（Underflow）被硬件截断为 0** 或**近零次正规数（Subnormal）的处理差异**。

## 三个经典 Case 的深度归因（§IV-D）

这三个 Case 完整展示了“从宏观差异一路追查到硬件底层汇编”的标准范式：

* **Case 1：数学库实现差异引发累积漂移（`Num↔Num`，Figure 4）**
  * **算式**：`fmod(1.5917e+289, 1.5793e-307)`
  * **表现**：`nvcc -O0` 输出 `1.4424e-307`，而 `hipcc -O0` 输出 `7.1923e-309`（差了两个量级！）。随后该值进入 `for` 循环累加，误差被指数级放大。
  * **汇编定位**：
    * AMD `hipcc` 生成了对外部 Clang 运行时库函数 **`__ocml_fmod_f64`** 的显式调用；
    * NVIDIA `nvcc` 则直接利用 **PTX/SASS 汇编**，内联生成了一组浮点运算与位操作指令（Bitwise manipulation）组合。
    * **结论**：两家底层数学库算法实现不同，对接近次正规数的模运算截断点不同。

* **Case 2：底层指令边界异常导致“除零成 Inf”（`Inf↔Num`，Figure 5）**
  * **算式**：`tmp_1 / ceil(+1.5955E-125)`
  * **表现**：`nvcc -O0` 输出 **`Inf`**；`hipcc -O0` 输出正常的 `1.34887e-306`。
  * **汇编定位**：
    * 数学上，对极小正数向上取整，`ceil(1.5955e-125)` 显然应等于 `1`（AMD 正确输出了 1，除法正常）；
    * **NVIDIA PTX/SASS 在处理此极小浮点数时发生异常，居然返回了 `0`！** 直接导致后续算式分母为 0，引发除零溢出坍塌为 `Inf`。
    * **结论**：证实了即便是成熟的工业级编译器，在特定极小数值边界下其内联汇编也会产生逻辑 Bug。

* **Case 3：优化引发指令重排，语义坍缩（`Inf↔NaN`，Figure 6）**
  * **表现**：在 `-O0` 时两端均输出 `-inf`（完全一致）；但在开启 `-O1` 后，`nvcc` 保持 `-inf`，而 `hipcc` 变成了 **`-nan`**。
  * **汇编定位**：
    * 代码中包含类似 `(-inf) + fabs(...)` 的中间量。在 `-O0` 下，按序执行保留了 `-inf`；
    * 开启 `-O1` 后，`hipcc` 调整了循环退出后表达式的求值顺序，中间步骤触发了类似于 `(-inf) - (-inf)` 或 `0 * inf` 的未定义算术，导致结果被毒化成 `-nan`。
    * **结论**：编译优化重排改变了中间值的生命周期与求值顺序，打破了边界情况下的计算语义。

## 疑问

* [x] **Q1: Varity 是否开源？如何生成程序？**
  * **答：开源**。GitHub 地址：[`https://github.com/LLNL/Varity`](https://github.com/LLNL/Varity)。
  * 它采用**上下文无关文法（CFG）**驱动：定义了变量类型、算术算符 `{+, -, *, /}`、数学库函数（`cos`, `sqrt`, `fmod` 等）、嵌套循环结构 `L1 > L2 > ... > LN` 和条件分支。生成器通过递归展开语法树构造 Kernel，并随机采样浮点数（涵盖正常数、极大/极小数）作为测试输入。
* [x] **Q2: 数学库差异的具体定位过程？**
  * **答：插桩打印中间量 + 反汇编对比**。
    1. 在 Kernel 内部关键算式后插入 `printf` 打印中间变量，缩小出现差异的代码行；
    2. 使用 `cuobjdump -sass` 查看 NVIDIA SASS 汇编，使用 `llvm-objdump -d` 查看 AMD ISA 汇编；
    3. 观察该数学函数是**调用了外部 runtime 库**（如 AMD 的 OCML 库）还是**被编译器内联展开为特定指令序列**（如 NVIDIA 的 PTX 指令组）。
* [x] **Q3: 如何避免将 run-to-run 波动误判为跨平台差异？**
  * **答：Varity 生成的 Kernel 本身是单线程确定的**。
    * 它的测试 Kernel 内部没有跨线程归约（Warp Shuffle）、没有多线程竞争、没有 `atomicAdd`。每次运行是单线程严格按序执行（或者多线程独立执行相同逻辑），因此在**同一块 GPU 上天然具有 100% 的确定性**（Run-to-run 差异为 0）。这保证了它捕获到的差异纯粹来自跨平台/跨编译器，而非并发调度的随机性。
* [x] **Q4: 对 reduction 类程序，它有没有单独统计？**
  * **答：没有单独作为一类算子统计**。
    * Varity 的文法里有 `for` 循环累加（类似于 `comp += array[i]` 的串行求和），但**它没有测分布式/并行归约树（Parallel Reduction Tree）**。这是该论文的一大空白，也恰恰是**本课题切入的核心机会点**！

## 启发

1. **“解耦元数据”测试框架**：
   * 采用统一的输入格式（保存为 `.npy` 或 `.pt` 二进制文件），不要两端各自随机生成；
   * 测试流程：`输入生成与固化 ──► GPU 加载执行 ──► NPU (torch_npu) 加载执行 ──► CPU FP64 (Oracle 参考) ──► 差分与残差分析`。
2. **采用升级版的“7 分类 + 相对误差”体系**：
   * 保留它的 7 类互斥判定（NaN, Inf, Zero, Number），这对于抓取昇腾 Vector/Cube 单元的 **FTZ（Flush-to-Zero）截断行为**极度有效；
   * 针对 `Num↔Num`，进一步细分：$\text{RelErr} < 10^{-5}$（安全舍入）、$10^{-5} \sim 10^{-2}$（算法/累加树差异）、$> 10^{-2}$（严重精度丢失/降精度故障）。
3. **单变量消融排查法则（Ablation）**：
   * 学习论文定位 Case 1/2 的手法：从完整的复杂算子中剥离出最小计算片段；
   * 昇腾侧重点消融变量：`allow_hf32` 开闭、`precision_mode`（`force_fp32` vs `allow_fp32_to_fp16`）、CANN 算子内联与融合开关。

| :--- | :--- | :--- |
| **编程模型** | 同属类 CUDA 体系（CUDA vs HIP，API 高度映射） | **异构隔阂更深**（CUDA/PTX vs CANN/Ascend C/达芬奇架构） |
| **计算模式** | **单线程标量控制流**（单线程内循环累加） | **高并行张量计算**（Warp 级折半归约、Cube 矩阵分块切分） |
| **浮点非结合律来源** | 编译器优化重排指令顺序 | **并行拓扑结构不同**（GPU 32-thread Warp vs 昇腾 128/256-element Vector 指令） |
| **测试输入构造** | 纯随机程序 + 随机输入生成器（Blind Fuzzing） | **针对性对抗构造**（正负湮灭、大数吃小数、极端动态范围、病态矩阵） |
| **真值基准** | 仅做 A vs B 差分，**无 Ground Truth**（不知谁对谁错） | **引入 CPU FP64 / MPFR 作为 Oracle**，能定量评价“谁更准” |

* **放弃“大而全的随机代码生成”**：Varity 维护语法树的成本极高，且针对的是通用 C/C++ 语言。我们研究的是**张量算子**，应该聚焦在**确定性算子 + 极具杀伤力的合成输入（Synthetic Inputs）**。
* **第一个杀手级实验设计（求和归约 Reduction）**：
  * 构造一个长度为 $N=10^6$ 的数组：$[10^4, -10^4, 10^{-3}, 10^4, -10^4, 10^{-3}, \dots]$；
  * 分别送入 `torch.sum`（GPU vs NPU），并对比 `numpy.sum(dtype=float64)`；
  * 观察两端是否因为**并行分块规约顺序不同**发生灾难性抵消（Catastrophic Cancellation）。这可以直接证明论文 5 所讲的“非结合性”在国产算力迁移中的现实杀伤力。
