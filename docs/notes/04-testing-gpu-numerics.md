## 一句话

用一个**小程序生成器 + 差分测试**，在 65 万次运行中找出 NVIDIA 与 AMD 之间由数学库、FP 精度和
代码转换（HIPIFY）引起的细微数值差异。

## 方法（本课题的最小可行版本可以直接照抄结构）

```
Varity 生成器 ──► 数千个短小的 CUDA 数值程序 + 输入
                    │
                    ├── nvcc  编译 ──► NVIDIA 运行 ──► 结果 A
                    └── hipcc 编译 ──► AMD    运行 ──► 结果 B
                                         （另用 HIPIFY 把 CUDA 转 HIP 再比一次）
                    │
                    └── 差分比较：A vs B（7 类结果分类）
```

- **优化级别作为独立变量**：`-O0/-O1/-O2/-O3/-O3 -ffast-math`。
- **结果分类（很实用的分类法）**：NaN / Inf / **Zero** / Number 两两组合共 7 类：
  `NaN↔Inf`、`NaN↔Zero`、`NaN↔Num`、`Inf↔Zero`、`Inf↔Num`、`Zero↔Num`、`Num↔Num`
  （把 Zero 单独拿出来，是为了捕捉「次正规数 / 近溢出值舍入成 0」）。
- **两台机器**各含 NVIDIA 与 AMD GPU，共跑 652,600 次。

## 结果

| 配置 | 程序数 | 运行次数 | 差异率 |
| --- | --- | --- | --- |
| FP64 | 3,540 | 247,500 | **0.98%** |
| FP64 + HIPIFY 转换 | 3,540 | 247,500 | **1.10%** |
| FP32 | 2,840 | 157,600 | **9.00%** |

- **FP32 的差异率高一个数量级**，且 `-O3 -ffast-math` 下最严重（13,877 次 vs `-O0` 的 45 次）。
- **`-O3 -ffast-math` 不是唯一元凶**：FP64 下 `-O0` 也有 440 次差异 —— 说明**无优化也可能不一致**。
- **`Num↔Num` 在所有优化级别下都占多数**：真实数值偏差（而非 NaN/Inf 语义差异）是主要形态。
- **HIPIFY 会引入新差异**（1.10% > 0.98%）：**代码转换本身**就是一个差异源。
- 差异的三大来源：① 数学库调用（如 `fmod`）② FP64 vs FP32 精度路径 ③ HIPIFY 转换。

### 一个案例的精度

同一输入，`nvcc` 输出 `8.6551990944767196e-306`，`hipcc` 输出 `9.3404611450291972e-306`
—— 都在次正规数区间，靠对比**中间结果的汇编**定位到原因。这类「极端量级才暴露」的模式，
和论文 3 的 violation signature（「仅当量级 > 2^12」）思路一致。

## 可复用到本课题的做法

- **从几十行的最小片段入手**，而不是先跑大模型：差异可解释、可缩减、可逐个排除。
- **优化级别 / 编译选项作为显式实验维度**：NPU 侧对应 CANN 的编译选项、`torch.compile` 开闭。
- **7 类结果分类法**：直接用于我对比 GPU/NPU 输出（尤其 Zero vs 次正规数）。
- **两种比较同时做**：同源码不同编译器（对应「两端各自 PyTorch 实现」）、转换后的代码（对应「算子变体」）。
- **中间量比对 + 汇编/IR 阅读**：当差异只在极端输入出现时，这是唯一能定性的手段。

## 与我的课题差异

- 它比的是 **NVIDIA vs AMD（同生态、同编程模型 CUDA/HIP）**；我比的是 **GPU vs 昇腾 NPU**，
  编程模型不同（CANN/Ascend C），无法直接互相编译。
- 它靠**自动生成程序**找差异；我的规模小得多，更适合**手工构造针对性输入 + 单因素变换**。
- 它不关心「相对高精度参考的误差」，只做两端差分 —— 我需要补上参考值这一维。
