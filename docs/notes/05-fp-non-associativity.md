## 一句话

浮点加法不满足结合律 → 并行归约的求和顺序不定 → 同一程序**重复运行结果不同**；
本文量化这种波动的统计性质，并评估用确定性实现（含 GPU 上的确定性归约、PyTorch 确定性开关、
确定性硬件 Groq）来换取可复现性的**性能与生产力代价**。

## 关键认识

- 异步/原子累加等价于对数组施加一个**未知的随机置换**再顺序相加：
  `S_ND = Σ x_{P(i)}`，而 `S_D = Σ x_i`。
- 这种差异在迭代求解器里会**累积**：文中提到特定 HPC 场景下 6~7 次迭代后误差可达 20%。
- 后果：正确性测试失效（波动接近甚至超过容差）、商业认证受阻、鲁棒性评估失真。

## 三个可复用的度量（本课题的 run-to-run 指标）

| 指标 | 定义 | 说明 |
| --- | --- | --- |
| `V_s(f)` | `1 − |f_ND / f_D|` | 标量输出的位级非确定性；两端位级相同则为 0 |
| `V_ermv(f)` | `(1/D) Σ |A_i − B_i| / |A_i|` | 数组输出的**逐元素相对平均变化** |
| `V_c(f)` | `(1/D) Σ 1(A_i ≠ B_i)` | **不同元素的占比**（计数型，最直观） |

三者都是 `V = 0 ⇔ 位级相同`，且随波动单调增大 —— 对报告「跨平台差异」同样适用。

### 文中给出的一个直观例子

FP64、`x ~ N(0,1)`、长度为 100 的求和，随机置换后 `S_nd − S_d ≈ −1.78e-15`，
`V_s ≈ −2.22e-16`（即 1 个 ULP 量级）；长度到 1e6 时差值可达 `4.26e-13`。
这个量级**低于**常见 `atol=5e-4` 的判定阈值 → **容差型测试根本发现不了**，但会毁掉迭代算法。

## GPU 上实现确定性归约的几种方案（§III）

1. **(i) 只用 `atomicAdd`**：最简单，但执行顺序取决于运行时 → 仍然非确定。
2. **(ii) 多个 kernel 之间的隐式全局同步**：分阶段，顺序固定。
3. **(iii) 单线程计算**：确定但最慢。
4. **(iv) `__threadfence`**：固定跨块累加顺序。

(ii)/(iv) 采用**成对（pairwise）+ 数据分块**：每轮 `t_i = x_i + x_{i+n/2}`，重复 `log2(n)` 次，
块内用 `__syncthreads`、共享内存；块间按固定顺序合并部分和。这正是「同一数学任务、不同实现」的对照组范本。

## PyTorch 确定性选项的评估（对课题直接相关）

- PyTorch 已提供 `torch.use_deterministic_algorithms(True)` 及相关环境变量；
  文中在 GPU 部署场景下检验它们**是否真的覆盖了**所有触发 run-to-run 波动的输入参数。
- 结论方向：文档的**完整性与可靠性不足**，某些情况下仍会出现波动 —— 需要自己验证，不能只看文档。
- 另评估用 **Groq** 这类确定性硬件承担推理部分，作为「硬件层面保证确定性」的路线。

## 可复用到本课题的做法

- **先测 run-to-run，再测跨平台**：同一设备重复 N 次得到基线波动 `V_0`，
  跨平台差异必须显著大于 `V_0` 才有意义（否则是「同一平台随机性」被误读）。
- **三指标并列报告**：标量用 `V_s`，向量用 `V_c`（有多少元素不同）和 `V_ermv`（平均相对偏离）。
- **成对求和作为「确定性基线」实现**：在 PyTorch 里就是 `chunk` 后再 `sum`，或固定顺序的 Python 循环。
- **性能代价要一起报**：确定性是有代价的（论文 2 说固定顺序最高 20%），
  只报「结果更一致」而不报开销，说服力不足。
- **不要迷信官方开关**：`use_deterministic_algorithms` 在 NPU 后端是否生效必须实测。

## 与我的课题差异

- 它关注**同一平台内的 run-to-run**；我关注**跨平台**，但完全可以共用一套指标。
- 它面向 HPC + DL 混合负载与大规模迭代；我的规模小，可以做到逐元素、逐 ULP 的细粒度分析。
- 硬件（Groq）路线对我不适用，但「硬件级确定性」这一维度可以作为讨论部分的对照。
