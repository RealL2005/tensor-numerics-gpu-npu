### 第三轮（同日续）：扩展到 `dot` / `matmul`

- `e20_dot.py`：FMA 判别器（`x=[2⁻²⁴,1+2⁻¹²]`, `y=[1,1+2⁻¹²]`，单次调用即可分辨"乘积是否被先舍入"）
  + 同一探针下 `sum(x*y)` / `dot` / `mv` / `mm` / `inner` 的 A。
- `e21_gemm_precision.py`：GEMM 逐元素 `A_elem = |err|/(u·Σ_k|a·b|)`，用于排除 HF32/低精度累加。
- 结果：见 `results/e20_dot.json`、`data/npu_dot_out.json`、`results/e21_gemm.json`、`data/npu_e21.json`。
  1. **API 档位差 8300 倍**（CPU，n=2²⁰，x 全 1，y 为对抗探针）：
     `np.sum(x*y)` A=8.0、`torch.sum(x*y)` 19.6、`torch.dot` 2080、`np.dot` 16654、`torch.mv` 8329、
     `torch.mm` 66636（全部逐次确定）。昇腾侧 `sum`/`dot` A=2.2 而 `mv`/`mm` A=515。
     RTX 4050 上四个 API 全走同一 reduce kernel，A=6~10，没有 API 差。
  2. **FMA 语义随 API 变**：`dot` 在四端都是"乘积先舍入"；`mv`/`mm` 在 CPU 与昇腾上是"精确乘加"。
  3. **排除 HF32 怀疑**：256³/1024³ GEMM 的 `A_elem` 中位数 GPU 0.12~0.19、昇腾 0.23，
     两端都是标准 fp32 累加 → §7.1 的巨大放大来自 K 轴归约顺序，不是精度被降。

### 第四轮：`matmul` 的 split-K 阈值

- 用同一探针扫 K（`results/e22_splitk.json`）：GPU `mm`/`mv` 的 A 在 K≤2²⁰ 时 0.6~9.3，
  **K=2²¹ 一步跳到 245.5**，之后 K 每翻倍 A 翻倍（422→755→1259，线性）；
  CPU `mm` 的 A 全程 ∝K（2¹⁶: 2864 → 2²⁴: 491750，A/K≈0.03）；
  两端 `sum(x*y)` 全程平坦（5~26）。
- 结论：`matmul` 的最坏误差是 **K 的阶跃+线性函数**，与平台优劣无关；
  跨平台 GEMM 对比必须在 split-K 阈值两侧各取一点。

### 第六轮：定下主线 —— 链 vs 树 的定量定律

- 先自我否决两条：①上一条"同质 ⇒ 单向偏置"经退化度扫描（ℓ=1…2²⁰）证伪；
  ②"单参数链长" `A=0.51·L` 被 w 扫描（`e27`）证伪：固定占用宽度只改精确宽度 w，
  A 从 −520 崩到 0，说明 L 不是守恒量。
- 得到结论（`e28`）：只改累加器**内部结构**（顺序链 → 二叉折半），在最坏输入下
  A 从 **5.33×10⁵ 掉到 1.6（差 33 万倍）**，且树形时 A 与占用宽度（4…2²⁰）**无关**。
  ```
  顺序累加器: A_max = 0.51·(内部链长−1) + O(1)
  树形累加器: A_max = O(1) ≤ 2
  ```
- 用它反演四个真实后端：numpy 链长≈16（独立结构探针也给出 16 ✓）、torch-CPU≈31、
  RTX 4050≈11、**昇腾=树形**（占用 16384 但 A≈1.9，此前无法自洽的现象被解释）。
- 这条把我这一整天的测量收束成一个可证伪的主线：**最坏误差由"是否树化 + 内部链长"决定，
  与并行度/占用宽度无关**；副产品是一个黑盒诊断量（一次 `A_adv` 测量即可给后端分型）。

### 第七轮：第二个独立探针 + 互证

- 新探针 E29：固定 `±1` 间距 d，数"有多少个 r 被吞"。在结构已知的模型上标定出三种签名
  （纯链 / 纯树 / 混合），再上真机。np32 的签名与 numpy pairwise 模型**逐点相同**（30,62,126,0,1,3,7,254,510,511）。
- 互证结果（`results/e30_two_probe_check.json`）：numpy 结构探针 16 vs A_adv 17.7 **一致**；
  torch-CPU 64 vs 37（差 1.7 倍，已解释为"占用 vs 顺序深度"，正是三宽度框架的预测）；
  RTX 4050 该方法失效（p,q 同累加器）；昇腾 5 vs（A 太小测不出）。
- **宽窗口（4096）复核推翻了我自己半小时前的判读**：torch-CPU 的占用不是 64 而是 **512**，
  而顺序深度只有 33 → occ/R=15.5，判读从"链"改成"树"。教训：结构探针的窗口必须大于一个累加器的占用，
  否则读数被截断（第一版窗口 512 就踩了这个坑）。判据最终收敛为：`occ≈R ⇒ 链；occ≫R ⇒ 树`。
- **昇腾"树形"得到第二条独立证据**：d=64/128/256 吞数塌到 3/1/0（同一 64-lane），d=512 → 511（跨 chunk），
  d<64 时吞数 ∝ d 且逐级翻倍 = LCA 子树形状 ⇒ lane 间为树。

### 第八轮：占用计量器 + "占用不是一个数"

- 新增 E31（内外双计数）：在 **RTX 4050** 上读出**占用 = 4**（E29 完全读不出），与 E12 的 4 元素粒度独立吻合。
- 同时发现判据的边界：numpy / torch-CPU 是**跨步**累加器（stride 8 / 32），"区间外"窗口本身就含同 lane 元素，
  判据失效。→ 方法论结论：**"占用"必须按布局选探针**（连续用内外计数、跨步用 d=1 网格），
  用错会得到反向结论（第一版就把 CPU 判成链）。
- 汇总出四端的完整刻画（§11.7）：numpy 8-lane 树+16 链 / CPU 32-lane 树(占用 512, 深度 33) /
  4050 vec4×长链(深度 35.6) / **昇腾 64-lane 树+chunk 树(深度 2–4) → 最准**。
  最坏误差排序完全由顺序深度 R 决定。

### 第九轮：步长直测 → "宽度谱"框架

- E32 的单探针"同链"原语有逻辑漏洞（r 落在第三条链上就永远存活），但 E33 用正确形式
  （扫 d，找**吸收数恰为 0** 的 d）把步长直接测出来：numpy **8**、torch-CPU **32**、
  RTX 4050 **1（连续组 4，d=4 突跳）**、昇腾 **1（d≤7 近零，d=8 突跳 → 连续组 8；另有跨步 64、chunk≈512）**。
- 由此把刻画升级为**嵌套宽度谱** `(g, s, c, R)`：四家把同样的总并行度分配在不同层级上，
  而最坏误差只由**顺序深度 R** 决定（昇腾每层树化 → R=2–4 最浅 → 最准；4050 组内 4 + 长链 → R=35.6）。
- 这也说清了与论文 [2] 的分工：GEMMDesc 判定**位级等价**；我们的主张是**误差幅度**只取决于 R，
  位级是否等价不影响幅度。

### 第十轮：定律补上"典型输入"，并做一次真正的预测

- E34：n=2²⁰ 扫 `占用 × 内部结构 × 输入类型`。链：`A_max~occ^0.99`、**`A_typ~occ^0.45`**；
  树：两者都是**常数**（A_max≈1.5, A_typ≈2.3e-3）。两个交叉点：最坏 R≈3、典型 R≈33。
- E35：用**只有对抗探针能测出的 R** 预测另一类输入（随机符号 8 种子 RMS）的误差：
  numpy 1.45×、torch-CPU 1.49×、RTX 4050 1.09×（相对 `4e-4√R`）。这是全篇唯一一处"预测"。
- 校准结论：**最坏/典型 ≈ 1275·√R**，即对抗探针给的是保证上界，真实负载通常低 10³~10⁴ 倍
  （CPU: A_max=18 vs A_rms=3.4e-3，差 5300 倍）。这条必须写进论文，否则 A_max 的数字会吓人 3~4 个数量级。

### 第十八轮：R1 第一个里程碑 —— 昇腾 sum 在 n≤8192 上逐比特复现

用户判断"让真实训练崩掉"不现实，因此改路线：**后果改为"逐比特复现"**（二元判据，秒级、无法辩解）。
- 做法：把候选归约顺序列成有限空间，小 n 上逐比特筛选，按失败点补下一层。四轮（e43/e45/e46/e47）。
- **结果**：4 行零参数模型在 n=1024/2048/4096/**8192** 上各 **80/80 逐比特**（三族输入：N(0,1)、|N(0,1)|、U(0,1e-3)）：
  `lane = i mod 64`（相差 64 的倍数同累加器）→ lane 内 **16 元素一段、段内跨步折半、段和跨步折半**
  → 64 个 lane 和用**连续折半**合并。
- **边界**：n≥12288 失效（33/60），且"连续 8192-chunk + 树"这类二层假设**全部失败**（≤7/20）→ 第二层不是连续 tile，
  下一轮改用探针定位而不是继续猜。
- 意义：这条把 §11 的经验律降级为"大 n 时可选的界"；在单 tile 区间内模型直接给精确误差。
  也是本报告唯一一处二元判据的结果。

### 第十九轮：第二层定位（得到两条硬信息，未破解）

- E48：用 (p,q)=(0,1) 的被吞集合定位"抵消有多局部"：
  n=4096 覆盖全数组（31 个 64-周期 ×2 = 62 个），**n=16384 只有前 5 个周期（8 个）**
  ⇒ n≥12288 出现**块局部**的第二层（约 320 元素的子树内就抵消了）。
- E49：按此测"块大小 × 块内沿用已验证模型 × 块间合并"共约 30 个模型（B∈{256…8192}×D∈{8,16}×3 种合并）：
  **全部失败**（16384 最好 6/20，32768 最好 10/20）⇒ 第二层不是"连续分块再合并"。
- 结论：第二层更可能是**融合在访存/线程映射**里（lane 与块编号交错），要继续必须换成 tree 重建
  （FP41 式 (p,q,s) 判定器，单条 lane 的 256 个元素，约 2–5k 次探针），已写进 plan。

### 第二十轮：第二层未破解，但把搜索空间砍掉并锁定了失败层

- E49/E50/E52：共约 **100 个参数化模型**（连续块 B∈{256…8192}、交错 tile、lane 步长 64/128/256 × 内层 5 种 × 合并 3 种）
  **全部不匹配**（最好 6~10/20）→ 第二层不是"分块再合并"、也不是"lane 步长变化"。
- E51：**单 lane 对抗探针**（只有同一条 lane 的亚 ulp 元素参与）把失败层锁定了：
  n=16384 时设备 k=**−0.56**，`pw_contig` 候选正好 −0.56 ⇒ **lane 内部是树（连续折半）**，
  所以失效在 **lane 的划分/合并**，不在 lane 内部。n=65536 时 k=−2.51、所有候选都对不上 ⇒ 第二层在大 n 上还会污染 lane 内部。
- 判断：继续参数化猜测边际收益已很低。下一步改成**直接重建**（(p,q,s) 判定器恢复单条 lane 的 256 元素合并顺序，2–5k 探针）。

### 第二十一轮：模型推广到 2-D（正面结果）

- 把 §11.22 的 1-D 模型**原样**（零改动）用于 2-D `sum(dim=1)`：C=1024/2048/4096 各 **8/8 行逐比特**；
  1-D 对照 20/20。
- 同一台卡、同一归约长度 1024，改成 `sum(dim=0)`（跨行、非连续）：**17/64**（随机水平）
  → **单变量对照**证明"结构跟着访存布局走，不跟着硬件走"。
- 意义：模型从"某个形状"变成"沿连续维的一次归约"，覆盖末维 softmax/LayerNorm 分母这类最常见的形状，
  判据仍是二元。

### 第二十二轮：形成交付件（`ascend_sum_model.py`）

- 把已验证的模型打包成模块 + `--self-test`：昇腾上 160 次 sum，**n=1024/2048/4096/8192 各 40/40，PASS**。
  实用价值：**不连 NPU 也能算出该设备 sum 的逐比特结果** → 无 golden 的位级回归测试 / 差分测试 oracle。
- `sum(dim=0)`（跨步）结论：逐比特最好 20/64（无候选命中），但 `A_adv = 0.88 ± 0.19`（链应 ≈537）
  ⇒ **"不同的树、同一精度等级"**。这解释了生态事故的形态：位级测试会红、精度测试不会红。
- 适用域写死在模块 docstring 里：950PR + CANN 9.1.0 + torch_npu 2.7.1，fp32，连续末维，n≤8192。

### 第二十三轮：兄弟对判定 —— 找到第二层难啃的原因

- 新原语：**兄弟对判定**（若 p、q 是兄弟，`+1/-1` 在此抵消，其它位置的 r 全存活 ⇒ 吸收集为空）。
- 在 n=16384 的 lane0 前 8 个元素（数组位置 0,64,…,448）上测 28 对：
  兄弟 = {(0,4), (1,3), (5,7)}，**既不等于跨步折半的 (0,4),(1,5),(2,6),(3,7)，也不等于连续折半**，
  且不是完美匹配（2、6 落单）。
- 结论：**该层级的折叠置换非保序** → 解释了为何 E49~E52 的 ~100 个参数化模型（都隐含保序假设）全部失败。
  下一步必须按置换重建，而不是继续试参数。

### 第二十四轮：第二层仍未被破解，但模型适用域扩了四向

- E56：分层递归模型（把 ≤8192 的结构当一层规则递归）24 个候选**全部失败**（≤8/20）。
- 换问"树是设备属性还是版本属性"：run 服务器所有 env 的 torch_npu 都是 2.7.1.post7.dev20260707，
  **拿不到版本对照**，该问题留白。
- E57（有效）：模型适用域四向扩展，全部逐比特通过——2-D C=8192（4/4）、`mean`==sum/n（4/4）、
  **fp16 输入 + fp32 输出（4/4）**、**bf16 输入 + fp32 输出（4/4）**。
  → 现在覆盖：3 种输入 dtype × 2 类形状 × 2 种算子，条件"fp32 累加、长度 ≤8192"，全部逐比特。

### 第二十五轮：结构指纹重建 —— 方法自证 + 第二层的局部尺度

- 新方法：对 lane0 前 16 个元素测**全部 120 对**的"被吞集合"，得结构指纹（信息量远大于 20 个输出比特）。
  **自证**：n=8192 上设备与模型 **120/120 对完全一致** → 方法可靠。
- n=16384 的指纹：`|A(0,b)| = 3,1,3,0,14,14,14,14,14,8,8,8,8,8,14`。
  其中 b=1..4 只有 0~3、b≥5 全部 ≥8 ⇒ **0 的子树在底层只覆盖约 5 个 lane 元素（~320 个数组元素）**，
  与 E48 独立测得的"被吞集合只到位置 257"吻合。
- 结论改写：第二层不是"配对顺序错了"，而是**累加器跨度从整条 lane 缩到 ~320 元素**。
  320 不是 2 的幂、16384/320 不整除 ⇒ 不是简单 chunk；这是下一步要解释的点。

### 第二十六轮：交付件扩两项（3-D 覆盖 + 同树判定）

- `(2,3,C) sum(dim=-1)`，C=1024/4096/**8192**：各 **6/6 逐比特** → "沿连续末维的一次归约"这一族
  （1-D / 2-D dim=1 / 3-D dim=-1）全部由同一 4 行模型覆盖。
- 交付件新增 `fingerprint()` 与 `same_tree(f,g,n)`：用 16 叶结构指纹判定两实现是否同树。
  实测 n=8192 → **120/120（同树）**；n=16384 → 32/120（不同树）。
  直接对应评审 §4.1 的 TreeReduceV2/CANN 案例，成本 ~3.4k 次小 sum（比 1436 个用例定位便宜一个量级）。

### 第二十七轮：第二层有了定量解释

- E61：用 (0,1) 的被吞集合跨度量"累加窗口"：n=8192 ≥64 lane 元素、**n=16384 = 5**、**n=65536 = 20**。
  ⇒ **窗口 ∝ n ⇒ 并行累加器个数近似恒定**：(n/64)/窗口 = 256/5 = 1024/20 = **51.2**（≈64 lane × 51 块 ≈ 3277 个）。
- 这就定量解释了为什么模型在 n≤8192 精确（一条 lane = 一个累加器），而 n≥12288 失效（累加器缩到 5 个 lane 元素）。
- 与 GPU 对照：ATen 是**阶跃**式加并行度，昇腾这里看起来是**平滑伸缩**。
- 仍未解决：为什么 ~51 块（51.2 非整数）；E60 按"块=320、块内 64 lane × 5"建的 27 个变体最好 6/20。

### 第二十八轮：第二层块边界测出，内部仍未知

- E62（直接测量）：窗口起点（lane 元素）= 0,5,10,15,19,24,29,34,38,… ⇒ **块大小 5,5,5,4 循环**
  = 数组元素 320,320,320,256，周期 1216；把上一轮的"51.2 个块"落成整数。
- E63/E64：用实测边界 + {块内 fold} × {64 lane 合并} × {块间合并}，合并含 **radix-4/8**，
  约 270 个候选最好 **8/20** ⇒ 边界对了但结合方式仍不在族里。
- 源码交叉确认：`TreeReduceV2.cpp: vectorBytes = 256` ⇒ **64 个 fp32 lane**，与黑盒测量一致；
  但解释不了 5 元素窗口（`numVectorRegisters=16` 也不等于 5）。
- 判断：候选族穷举收益≈0，要继续必须做逐层重建，或查 CANN 侧 tiling（不在本仓库）。

### 第二十九轮：在 CANN 安装目录里找到 reduce 源码，机制对上了

- 不用拉仓库：`/data/pri/cann-9.1.0/opp/built-in/op_impl/ai_core/tbe/impl/ops_math/ascendc/reduce_sum/`
  与 `.../common/atvoss/reduce/reduce_operator.h`（1511 行）是 AscendC 实现源码。
- **三条源码事实与我此前的三个测量逐条对应**：
  ① `CalcFolds(64)=6` ↔ 测到的 64 条 lane；
  ② `BASE_FOLD=4` + `tailFolds=folds%4`(0~3) ↔ 测到的块大小 **5,5,5,4**；
  ③ fold2/fold3 模板 `(v0+v2)+(v1+v3)`、`((v0+v4)+(v2+v6))+((v1+v5)+(v3+v7))`
     ⇒ **向量级折叠是跨步配对** ↔ 兄弟对 {(0,4),(1,3),(5,7)} 的"非保序"。
- 这解释了第二层为什么难：**源码里根本没有"连续配对"**，我那 ~270 个含连续配对的候选注定失败。
- 未读完：`fold1/2/3` 的分块公式、尾块与块间合并顺序；且 `torch.sum` 是否走这条 op 路径未证。

### 第三十轮：切片表定死（54 片），但装配仍失败

- E62 扩到 k≤129：窗口起点严格 **5,5,5,4 循环**（周期 19 lane 元素）⇒ n=16384 共 **54 片**
  （40 片 5 向量 + 14 片 4 向量，与 256=5a+4b, a+b=54 的解一致）。
- E65：按源码语义"每片产出 64-lane 向量、54 片先合并、最后折 lane"重建 → **4/20**；
  E63 的"每片先折标量" → 7/20。累计 ~300 个候选失败。
- 结论：第二层是"**5 条已知事实 + 1 个未知装配**"。缺的是片内 5 向量的精确顺序与 54 片的合并顺序，
  这两者不在 `reduce_operator.h`（kernel 模板）里，而在**未发布的 host 侧 tiling/调度**。

### 第三十一轮：逐层重建（用户指定走 1）—— 一个决定性结果 + 一个否定

- E66/E69：从**吸收集合**直接反推树形（无结构假设）。片内向量树 = `((0,4),2)+(1,3)`
  = **源码 fold3 模板 + 补零**；lane 树的兄弟对 = (0,1),(2,3),(4,5),(6,7)。
- E71（隔离，决定性）：只让一个 64 元素向量非零 → 设备输出就是一次 lane 折叠。
  **连续折半 12/12**，跨步 2/12，顺序 3/12 ⇒ **lane 折叠是连续的**。这推翻了我此前所有模型的假设。
- E72（隔离）：固定 lane=contig，单 slice 隔离下穷举 6 种向量折叠，最好 7/10、`strided` 0/10 ⇒
  **没有 10/10**，即"片内向量折叠 → lane 折叠 → 片间合并"这套分段复合**不成立**，
  真实实现更早就跨 lane 交织。

### 第三十二轮：三阶段树都测出，但"乘积"不成立 —— 存在 lane 置换

- E73：lane-first 分段也失败（最好 18/48）。
- E74（无假设锚点扫描）：q=向量1/2/3/4 → |A|=3/1/3/**0**，与 E66 完全一致（片内树 = `((0,4),2)+(1,3)`）；
  **q=下一 slice（位置 320）→ |A|=1022（全部）** ⇒ 片间在近根处才相遇。
- 结论：三阶段的树**各自都已测出**，但按它们装配的模型只有 6/20，且单 slice 隔离下无候选 10/10。
  **唯一自洽解释：片内向量折叠不是逐元素的，它做 lane 置换。**
  依据：E66/E74 的 ±1 放在同一 lane 内 ⇒ 只看见垂直树；E72 用整片数据 ⇒ 对 lane 置换敏感。
  这解释了为何 ~300 个"先折向量再折 lane"的候选全失败（都假设了逐元素）。

### 第三十三轮：否定 lane 置换、确认结构，但逐比特仍不成立

- E76（索引修正后的跨向量×跨 lane 探针）：吸收范围严格是 lane 区间 `[0,2^k−1]`，与同向量内测量一致
  ⇒ **没有 lane 置换**（否定 §11.32 的猜测）；且同 lane 跨 4 向量 |A|=0 ⇒ **垂直折叠先于 lane 折叠**。
- E77：按"垂直 fold3+补零 → 连续 lane → 片间树（10 种）"装配，最好仍只有 **6/20**。
- 方法论结论：**吸收集合只能确定"谁和谁相遇"，不能确定舍入次序**——两个不同的树可以有相同吸收模式。
  这是本方法的边界，也是第二层卡住的真正原因。

# 第二轮（同日晚）：第一轮实测跑通，拿到四端数据

## 今日完成

- **打通"输入 → 三端执行 → 外部精确参考 → 比较"的完整链路**：本地（numpy / torch-CPU / RTX 4050）
  与昇腾 950PR（卡 2，只跑指纹级脚本，每次几百次 `sum`）。三端输入 sha256 已对拍一致。
- 造出并校准了两类探针：
  1. **对抗排列探针**：`[1.0] + (n-1)×(0.9~1.1)·2⁻²⁵`。被吞掉的加法误差**精确等于被吞的加数**，
     于是 `A = |err|/(u·Σ|x|) = 0.525 × 被浪费的加法次数`。用 `seq` 模型校准：n=2²⁴ 时给出
     A = 1.68×10⁷ = n−1（误差 0.01%），证明探针测的正是"等效深度"。
  2. **三位非零元探针**：`x[p]=+1, x[q]=−1, x[s]=r=2⁻²⁵`，输出**必为恰好 0 或恰好 r**，
     噪声为零，可当结构探针也可当最小反例。
- 把 numpy 的 pairwise 求和写成 20 行模型，**45/45 逐比特吻合**（n=7…65536），并在 E15 每行与
  `np.sum` 逐比特相同 → 有了"已知答案"的锚点，误差从"测量"变成"可计算"。
- 结构读出：固定 (p,q) 扫 s，读出各后端的累加器链（numpy 步长 8/块长 128；RTX 4050 4 元素粒度；
  **昇腾步长 64**，(0,512)/(0,128) 直接抵消）。
- 发现并复现昇腾侧方法论级坑：**设备上 `tensor.double()` / `.to(float64)` 静默返回 fp32**。

### 第三轮（同日续）：扩展到 `dot` / `matmul`

- `e20_dot.py`：FMA 判别器（`x=[2⁻²⁴,1+2⁻¹²]`, `y=[1,1+2⁻¹²]`，单次调用即可分辨"乘积是否被先舍入"）
  + 同一探针下 `sum(x*y)` / `dot` / `mv` / `mm` / `inner` 的 A。
- `e21_gemm_precision.py`：GEMM 逐元素 `A_elem = |err|/(u·Σ_k|a·b|)`，用于排除 HF32/低精度累加。
- 结果：见 `results/e20_dot.json`、`data/npu_dot_out.json`、`results/e21_gemm.json`、`data/npu_e21.json`。
  1. **API 档位差 8300 倍**（CPU，n=2²⁰，x 全 1，y 为对抗探针）：
     `np.sum(x*y)` A=8.0、`torch.sum(x*y)` 19.6、`torch.dot` 2080、`np.dot` 16654、`torch.mv` 8329、
     `torch.mm` 66636（全部逐次确定）。昇腾侧 `sum`/`dot` A=2.2 而 `mv`/`mm` A=515。
     RTX 4050 上四个 API 全走同一 reduce kernel，A=6~10，没有 API 差。
  2. **FMA 语义随 API 变**：`dot` 在四端都是"乘积先舍入"；`mv`/`mm` 在 CPU 与昇腾上是"精确乘加"。
  3. **排除 HF32 怀疑**：256³/1024³ GEMM 的 `A_elem` 中位数 GPU 0.12~0.19、昇腾 0.23，
     两端都是标准 fp32 累加 → §7.1 的巨大放大来自 K 轴归约顺序，不是精度被降。

### 第四轮：`matmul` 的 split-K 阈值

- 用同一探针扫 K（`results/e22_splitk.json`）：GPU `mm`/`mv` 的 A 在 K≤2²⁰ 时 0.6~9.3，
  **K=2²¹ 一步跳到 245.5**，之后 K 每翻倍 A 翻倍（422→755→1259，线性）；
  CPU `mm` 的 A 全程 ∝K（2¹⁶: 2864 → 2²⁴: 491750，A/K≈0.03）；
  两端 `sum(x*y)` 全程平坦（5~26）。
- 结论：`matmul` 的最坏误差是 **K 的阶跃+线性函数**，与平台优劣无关；
  跨平台 GEMM 对比必须在 split-K 阈值两侧各取一点。

### 第六轮：定下主线 —— 链 vs 树 的定量定律

- 先自我否决两条：①上一条"同质 ⇒ 单向偏置"经退化度扫描（ℓ=1…2²⁰）证伪；
  ②"单参数链长" `A=0.51·L` 被 w 扫描（`e27`）证伪：固定占用宽度只改精确宽度 w，
  A 从 −520 崩到 0，说明 L 不是守恒量。
- 得到结论（`e28`）：只改累加器**内部结构**（顺序链 → 二叉折半），在最坏输入下
  A 从 **5.33×10⁵ 掉到 1.6（差 33 万倍）**，且树形时 A 与占用宽度（4…2²⁰）**无关**。
  ```
  顺序累加器: A_max = 0.51·(内部链长−1) + O(1)
  树形累加器: A_max = O(1) ≤ 2
  ```
- 用它反演四个真实后端：numpy 链长≈16（独立结构探针也给出 16 ✓）、torch-CPU≈31、
  RTX 4050≈11、**昇腾=树形**（占用 16384 但 A≈1.9，此前无法自洽的现象被解释）。
- 这条把我这一整天的测量收束成一个可证伪的主线：**最坏误差由"是否树化 + 内部链长"决定，
  与并行度/占用宽度无关**；副产品是一个黑盒诊断量（一次 `A_adv` 测量即可给后端分型）。

### 第七轮：第二个独立探针 + 互证

- 新探针 E29：固定 `±1` 间距 d，数"有多少个 r 被吞"。在结构已知的模型上标定出三种签名
  （纯链 / 纯树 / 混合），再上真机。np32 的签名与 numpy pairwise 模型**逐点相同**（30,62,126,0,1,3,7,254,510,511）。
- 互证结果（`results/e30_two_probe_check.json`）：numpy 结构探针 16 vs A_adv 17.7 **一致**；
  torch-CPU 64 vs 37（差 1.7 倍，已解释为"占用 vs 顺序深度"，正是三宽度框架的预测）；
  RTX 4050 该方法失效（p,q 同累加器）；昇腾 5 vs（A 太小测不出）。
- **宽窗口（4096）复核推翻了我自己半小时前的判读**：torch-CPU 的占用不是 64 而是 **512**，
  而顺序深度只有 33 → occ/R=15.5，判读从"链"改成"树"。教训：结构探针的窗口必须大于一个累加器的占用，
  否则读数被截断（第一版窗口 512 就踩了这个坑）。判据最终收敛为：`occ≈R ⇒ 链；occ≫R ⇒ 树`。
- **昇腾"树形"得到第二条独立证据**：d=64/128/256 吞数塌到 3/1/0（同一 64-lane），d=512 → 511（跨 chunk），
  d<64 时吞数 ∝ d 且逐级翻倍 = LCA 子树形状 ⇒ lane 间为树。

### 第八轮：占用计量器 + "占用不是一个数"

- 新增 E31（内外双计数）：在 **RTX 4050** 上读出**占用 = 4**（E29 完全读不出），与 E12 的 4 元素粒度独立吻合。
- 同时发现判据的边界：numpy / torch-CPU 是**跨步**累加器（stride 8 / 32），"区间外"窗口本身就含同 lane 元素，
  判据失效。→ 方法论结论：**"占用"必须按布局选探针**（连续用内外计数、跨步用 d=1 网格），
  用错会得到反向结论（第一版就把 CPU 判成链）。
- 汇总出四端的完整刻画（§11.7）：numpy 8-lane 树+16 链 / CPU 32-lane 树(占用 512, 深度 33) /
  4050 vec4×长链(深度 35.6) / **昇腾 64-lane 树+chunk 树(深度 2–4) → 最准**。
  最坏误差排序完全由顺序深度 R 决定。

### 第九轮：步长直测 → "宽度谱"框架

- E32 的单探针"同链"原语有逻辑漏洞（r 落在第三条链上就永远存活），但 E33 用正确形式
  （扫 d，找**吸收数恰为 0** 的 d）把步长直接测出来：numpy **8**、torch-CPU **32**、
  RTX 4050 **1（连续组 4，d=4 突跳）**、昇腾 **1（d≤7 近零，d=8 突跳 → 连续组 8；另有跨步 64、chunk≈512）**。
- 由此把刻画升级为**嵌套宽度谱** `(g, s, c, R)`：四家把同样的总并行度分配在不同层级上，
  而最坏误差只由**顺序深度 R** 决定（昇腾每层树化 → R=2–4 最浅 → 最准；4050 组内 4 + 长链 → R=35.6）。
- 这也说清了与论文 [2] 的分工：GEMMDesc 判定**位级等价**；我们的主张是**误差幅度**只取决于 R，
  位级是否等价不影响幅度。

### 第十轮：定律补上"典型输入"，并做一次真正的预测

- E34：n=2²⁰ 扫 `占用 × 内部结构 × 输入类型`。链：`A_max~occ^0.99`、**`A_typ~occ^0.45`**；
  树：两者都是**常数**（A_max≈1.5, A_typ≈2.3e-3）。两个交叉点：最坏 R≈3、典型 R≈33。
- E35：用**只有对抗探针能测出的 R** 预测另一类输入（随机符号 8 种子 RMS）的误差：
  numpy 1.45×、torch-CPU 1.49×、RTX 4050 1.09×（相对 `4e-4√R`）。这是全篇唯一一处"预测"。
- 校准结论：**最坏/典型 ≈ 1275·√R**，即对抗探针给的是保证上界，真实负载通常低 10³~10⁴ 倍
  （CPU: A_max=18 vs A_rms=3.4e-3，差 5300 倍）。这条必须写进论文，否则 A_max 的数字会吓人 3~4 个数量级。

  策略只按形状/flag 选（如 `directRegisterRA && plan.dimR <= 64`）→ 直接坐实评审"编译器不知道改了多少精度"。
- 由此把评审 §3.4 的重构意见落到具体行动：**测量对象改为"pass/flag 配置的 R 敏感度"**，而不是"后端指纹"。

### 第十五轮：用户侧 flag 能否定价 —— 负结果

  `vf_merge_level` 0/1/2、`enable_fp_fusion=False`、`enable_graph_optimize=False`
  → **A 全部是 11.03，一位不差**；FMA 判别器在开/关下都是"两次舍入"。
- 结论：triton-ascend 3.6.0 **没有向用户暴露"改归约结构"的通道**（`bisheng_options` 被标 `init=False`，
  整个 ascend backend 只有 1 个 `os.getenv`）。→ "flag → R 敏感度"这张表只能在编译器内部做（build 服务器侧）。
- 附带确认：**昇腾的 FMA 收缩只在 Cube/matmul 路径**（`mv`/`mm`/`inner` 一次舍入），vector 逐元素路径不收缩
  → "打开 FMA"是路径属性，不是全局 flag。与 §11.14 torch 层的结论一致。

### 第十八轮：R1 第一个里程碑 —— 昇腾 sum 在 n≤8192 上逐比特复现

用户判断"让真实训练崩掉"不现实，因此改路线：**后果改为"逐比特复现"**（二元判据，秒级、无法辩解）。
- 做法：把候选归约顺序列成有限空间，小 n 上逐比特筛选，按失败点补下一层。四轮（e43/e45/e46/e47）。
- **结果**：4 行零参数模型在 n=1024/2048/4096/**8192** 上各 **80/80 逐比特**（三族输入：N(0,1)、|N(0,1)|、U(0,1e-3)）：
  `lane = i mod 64`（相差 64 的倍数同累加器）→ lane 内 **16 元素一段、段内跨步折半、段和跨步折半**
  → 64 个 lane 和用**连续折半**合并。
- **边界**：n≥12288 失效（33/60），且"连续 8192-chunk + 树"这类二层假设**全部失败**（≤7/20）→ 第二层不是连续 tile，
  下一轮改用探针定位而不是继续猜。
- 意义：这条把 §11 的经验律降级为"大 n 时可选的界"；在单 tile 区间内模型直接给精确误差。
  也是本报告唯一一处二元判据的结果。

### 第十九轮：第二层定位（得到两条硬信息，未破解）

- E48：用 (p,q)=(0,1) 的被吞集合定位"抵消有多局部"：
  n=4096 覆盖全数组（31 个 64-周期 ×2 = 62 个），**n=16384 只有前 5 个周期（8 个）**
  ⇒ n≥12288 出现**块局部**的第二层（约 320 元素的子树内就抵消了）。
- E49：按此测"块大小 × 块内沿用已验证模型 × 块间合并"共约 30 个模型（B∈{256…8192}×D∈{8,16}×3 种合并）：
  **全部失败**（16384 最好 6/20，32768 最好 10/20）⇒ 第二层不是"连续分块再合并"。
- 结论：第二层更可能是**融合在访存/线程映射**里（lane 与块编号交错），要继续必须换成 tree 重建
  （FP41 式 (p,q,s) 判定器，单条 lane 的 256 个元素，约 2–5k 次探针），已写进 plan。

### 第二十轮：第二层未破解，但把搜索空间砍掉并锁定了失败层

- E49/E50/E52：共约 **100 个参数化模型**（连续块 B∈{256…8192}、交错 tile、lane 步长 64/128/256 × 内层 5 种 × 合并 3 种）
  **全部不匹配**（最好 6~10/20）→ 第二层不是"分块再合并"、也不是"lane 步长变化"。
- E51：**单 lane 对抗探针**（只有同一条 lane 的亚 ulp 元素参与）把失败层锁定了：
  n=16384 时设备 k=**−0.56**，`pw_contig` 候选正好 −0.56 ⇒ **lane 内部是树（连续折半）**，
  所以失效在 **lane 的划分/合并**，不在 lane 内部。n=65536 时 k=−2.51、所有候选都对不上 ⇒ 第二层在大 n 上还会污染 lane 内部。
- 判断：继续参数化猜测边际收益已很低。下一步改成**直接重建**（(p,q,s) 判定器恢复单条 lane 的 256 元素合并顺序，2–5k 探针）。

### 第二十一轮：模型推广到 2-D（正面结果）

- 把 §11.22 的 1-D 模型**原样**（零改动）用于 2-D `sum(dim=1)`：C=1024/2048/4096 各 **8/8 行逐比特**；
  1-D 对照 20/20。
- 同一台卡、同一归约长度 1024，改成 `sum(dim=0)`（跨行、非连续）：**17/64**（随机水平）
  → **单变量对照**证明"结构跟着访存布局走，不跟着硬件走"。
- 意义：模型从"某个形状"变成"沿连续维的一次归约"，覆盖末维 softmax/LayerNorm 分母这类最常见的形状，
  判据仍是二元。

### 第二十二轮：形成交付件（`ascend_sum_model.py`）

- 把已验证的模型打包成模块 + `--self-test`：昇腾上 160 次 sum，**n=1024/2048/4096/8192 各 40/40，PASS**。
  实用价值：**不连 NPU 也能算出该设备 sum 的逐比特结果** → 无 golden 的位级回归测试 / 差分测试 oracle。
- `sum(dim=0)`（跨步）结论：逐比特最好 20/64（无候选命中），但 `A_adv = 0.88 ± 0.19`（链应 ≈537）
  ⇒ **"不同的树、同一精度等级"**。这解释了生态事故的形态：位级测试会红、精度测试不会红。
- 适用域写死在模块 docstring 里：950PR + CANN 9.1.0 + torch_npu 2.7.1，fp32，连续末维，n≤8192。

### 第二十三轮：兄弟对判定 —— 找到第二层难啃的原因

- 新原语：**兄弟对判定**（若 p、q 是兄弟，`+1/-1` 在此抵消，其它位置的 r 全存活 ⇒ 吸收集为空）。
- 在 n=16384 的 lane0 前 8 个元素（数组位置 0,64,…,448）上测 28 对：
  兄弟 = {(0,4), (1,3), (5,7)}，**既不等于跨步折半的 (0,4),(1,5),(2,6),(3,7)，也不等于连续折半**，
  且不是完美匹配（2、6 落单）。
- 结论：**该层级的折叠置换非保序** → 解释了为何 E49~E52 的 ~100 个参数化模型（都隐含保序假设）全部失败。
  下一步必须按置换重建，而不是继续试参数。

### 第二十四轮：第二层仍未被破解，但模型适用域扩了四向

- E56：分层递归模型（把 ≤8192 的结构当一层规则递归）24 个候选**全部失败**（≤8/20）。
- 换问"树是设备属性还是版本属性"：run 服务器所有 env 的 torch_npu 都是 2.7.1.post7.dev20260707，
  **拿不到版本对照**，该问题留白。
- E57（有效）：模型适用域四向扩展，全部逐比特通过——2-D C=8192（4/4）、`mean`==sum/n（4/4）、
  **fp16 输入 + fp32 输出（4/4）**、**bf16 输入 + fp32 输出（4/4）**。
  → 现在覆盖：3 种输入 dtype × 2 类形状 × 2 种算子，条件"fp32 累加、长度 ≤8192"，全部逐比特。

### 第二十五轮：结构指纹重建 —— 方法自证 + 第二层的局部尺度

- 新方法：对 lane0 前 16 个元素测**全部 120 对**的"被吞集合"，得结构指纹（信息量远大于 20 个输出比特）。
  **自证**：n=8192 上设备与模型 **120/120 对完全一致** → 方法可靠。
- n=16384 的指纹：`|A(0,b)| = 3,1,3,0,14,14,14,14,14,8,8,8,8,8,14`。
  其中 b=1..4 只有 0~3、b≥5 全部 ≥8 ⇒ **0 的子树在底层只覆盖约 5 个 lane 元素（~320 个数组元素）**，
  与 E48 独立测得的"被吞集合只到位置 257"吻合。
- 结论改写：第二层不是"配对顺序错了"，而是**累加器跨度从整条 lane 缩到 ~320 元素**。
  320 不是 2 的幂、16384/320 不整除 ⇒ 不是简单 chunk；这是下一步要解释的点。

### 第二十六轮：交付件扩两项（3-D 覆盖 + 同树判定）

- `(2,3,C) sum(dim=-1)`，C=1024/4096/**8192**：各 **6/6 逐比特** → "沿连续末维的一次归约"这一族
  （1-D / 2-D dim=1 / 3-D dim=-1）全部由同一 4 行模型覆盖。
- 交付件新增 `fingerprint()` 与 `same_tree(f,g,n)`：用 16 叶结构指纹判定两实现是否同树。
  实测 n=8192 → **120/120（同树）**；n=16384 → 32/120（不同树）。
  直接对应评审 §4.1 的 TreeReduceV2/CANN 案例，成本 ~3.4k 次小 sum（比 1436 个用例定位便宜一个量级）。

### 第二十七轮：第二层有了定量解释

- E61：用 (0,1) 的被吞集合跨度量"累加窗口"：n=8192 ≥64 lane 元素、**n=16384 = 5**、**n=65536 = 20**。
  ⇒ **窗口 ∝ n ⇒ 并行累加器个数近似恒定**：(n/64)/窗口 = 256/5 = 1024/20 = **51.2**（≈64 lane × 51 块 ≈ 3277 个）。
- 这就定量解释了为什么模型在 n≤8192 精确（一条 lane = 一个累加器），而 n≥12288 失效（累加器缩到 5 个 lane 元素）。
- 与 GPU 对照：ATen 是**阶跃**式加并行度，昇腾这里看起来是**平滑伸缩**。
- 仍未解决：为什么 ~51 块（51.2 非整数）；E60 按"块=320、块内 64 lane × 5"建的 27 个变体最好 6/20。

### 第二十八轮：第二层块边界测出，内部仍未知

- E62（直接测量）：窗口起点（lane 元素）= 0,5,10,15,19,24,29,34,38,… ⇒ **块大小 5,5,5,4 循环**
  = 数组元素 320,320,320,256，周期 1216；把上一轮的"51.2 个块"落成整数。
- E63/E64：用实测边界 + {块内 fold} × {64 lane 合并} × {块间合并}，合并含 **radix-4/8**，
  约 270 个候选最好 **8/20** ⇒ 边界对了但结合方式仍不在族里。
- 源码交叉确认：`TreeReduceV2.cpp: vectorBytes = 256` ⇒ **64 个 fp32 lane**，与黑盒测量一致；
  但解释不了 5 元素窗口（`numVectorRegisters=16` 也不等于 5）。
- 判断：候选族穷举收益≈0，要继续必须做逐层重建，或查 CANN 侧 tiling（不在本仓库）。

### 第二十九轮：在 CANN 安装目录里找到 reduce 源码，机制对上了

- 不用拉仓库：`/data/pri/cann-9.1.0/opp/built-in/op_impl/ai_core/tbe/impl/ops_math/ascendc/reduce_sum/`
  与 `.../common/atvoss/reduce/reduce_operator.h`（1511 行）是 AscendC 实现源码。
- **三条源码事实与我此前的三个测量逐条对应**：
  ① `CalcFolds(64)=6` ↔ 测到的 64 条 lane；
  ② `BASE_FOLD=4` + `tailFolds=folds%4`(0~3) ↔ 测到的块大小 **5,5,5,4**；
  ③ fold2/fold3 模板 `(v0+v2)+(v1+v3)`、`((v0+v4)+(v2+v6))+((v1+v5)+(v3+v7))`
     ⇒ **向量级折叠是跨步配对** ↔ 兄弟对 {(0,4),(1,3),(5,7)} 的"非保序"。
- 这解释了第二层为什么难：**源码里根本没有"连续配对"**，我那 ~270 个含连续配对的候选注定失败。
- 未读完：`fold1/2/3` 的分块公式、尾块与块间合并顺序；且 `torch.sum` 是否走这条 op 路径未证。

### 第三十轮：切片表定死（54 片），但装配仍失败

- E62 扩到 k≤129：窗口起点严格 **5,5,5,4 循环**（周期 19 lane 元素）⇒ n=16384 共 **54 片**
  （40 片 5 向量 + 14 片 4 向量，与 256=5a+4b, a+b=54 的解一致）。
- E65：按源码语义"每片产出 64-lane 向量、54 片先合并、最后折 lane"重建 → **4/20**；
  E63 的"每片先折标量" → 7/20。累计 ~300 个候选失败。
- 结论：第二层是"**5 条已知事实 + 1 个未知装配**"。缺的是片内 5 向量的精确顺序与 54 片的合并顺序，
  这两者不在 `reduce_operator.h`（kernel 模板）里，而在**未发布的 host 侧 tiling/调度**。

### 第三十一轮：逐层重建（用户指定走 1）—— 一个决定性结果 + 一个否定

- E66/E69：从**吸收集合**直接反推树形（无结构假设）。片内向量树 = `((0,4),2)+(1,3)`
  = **源码 fold3 模板 + 补零**；lane 树的兄弟对 = (0,1),(2,3),(4,5),(6,7)。
- E71（隔离，决定性）：只让一个 64 元素向量非零 → 设备输出就是一次 lane 折叠。
  **连续折半 12/12**，跨步 2/12，顺序 3/12 ⇒ **lane 折叠是连续的**。这推翻了我此前所有模型的假设。
- E72（隔离）：固定 lane=contig，单 slice 隔离下穷举 6 种向量折叠，最好 7/10、`strided` 0/10 ⇒
  **没有 10/10**，即"片内向量折叠 → lane 折叠 → 片间合并"这套分段复合**不成立**，
  真实实现更早就跨 lane 交织。

### 第三十二轮：三阶段树都测出，但"乘积"不成立 —— 存在 lane 置换

- E73：lane-first 分段也失败（最好 18/48）。
- E74（无假设锚点扫描）：q=向量1/2/3/4 → |A|=3/1/3/**0**，与 E66 完全一致（片内树 = `((0,4),2)+(1,3)`）；
  **q=下一 slice（位置 320）→ |A|=1022（全部）** ⇒ 片间在近根处才相遇。
- 结论：三阶段的树**各自都已测出**，但按它们装配的模型只有 6/20，且单 slice 隔离下无候选 10/10。
  **唯一自洽解释：片内向量折叠不是逐元素的，它做 lane 置换。**
  依据：E66/E74 的 ±1 放在同一 lane 内 ⇒ 只看见垂直树；E72 用整片数据 ⇒ 对 lane 置换敏感。
  这解释了为何 ~300 个"先折向量再折 lane"的候选全失败（都假设了逐元素）。

### 第三十三轮：否定 lane 置换、确认结构，但逐比特仍不成立

- E76（索引修正后的跨向量×跨 lane 探针）：吸收范围严格是 lane 区间 `[0,2^k−1]`，与同向量内测量一致
  ⇒ **没有 lane 置换**（否定 §11.32 的猜测）；且同 lane 跨 4 向量 |A|=0 ⇒ **垂直折叠先于 lane 折叠**。
- E77：按"垂直 fold3+补零 → 连续 lane → 片间树（10 种）"装配，最好仍只有 **6/20**。
- 方法论结论：**吸收集合只能确定"谁和谁相遇"，不能确定舍入次序**——两个不同的树可以有相同吸收模式。
  这是本方法的边界，也是第二层卡住的真正原因。
